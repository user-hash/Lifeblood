# MCP Protocol Invariants

JSON-RPC 2.0 / MCP wire-format contracts, tool-registry shape, and the
truth envelope that ships on every read-side response. The protocol
contract is owned by `McpDispatcher` in `Lifeblood.Server.Mcp`;
`Program.cs` is a thin process-transport selector that delegates ordinary
stdio and shared-daemon requests to the same `McpServerHost` composition.
It contains no JSON-RPC method-string matching or response construction.
All protocol routing lives in `McpDispatcher`, which is a public sealed class
testable through its normal public API.

## Wire Protocol

- **INV-MCP-001. `initialize` response carries `protocolVersion` and `capabilities`.** Both are required by the MCP spec. `protocolVersion` is sourced from `McpProtocolSpec.SupportedVersion` via `McpDispatcher.SupportedProtocolVersion` (see INV-MCP-003). `capabilities` is a typed `McpCapabilities` POCO, never an inline dictionary, so new MCP capability negotiations are structural additions. Class-level defaults on `McpInitializeResult` plus explicit construction-site assignment make this belt-and-braces. Pinned by `McpProtocolTests.Initialize_ReturnsSpecCompliantResult`, `Initialize_SerializedJson_HasProtocolVersionAndCapabilities`, and `McpProtocolSourceOfTruthTests.McpDispatcher_InitializeResponse_AdvertisesSpecVersion`.

- **INV-MCP-002. Notifications never receive a response body.** Messages with `request.Id == null` are notifications per JSON-RPC 2.0. Recognized notification method names live in `McpProtocolSpec.AllKnownNotifications` (see INV-MCP-003). `McpDispatcher.KnownNotifications` is constructed directly from that set, so the two can never drift. Today's set: `notifications/initialized` (spec canonical), `initialized` (legacy alias during deprecation), `notifications/cancelled`, `$/cancelRequest`. Any entry short-circuits `Dispatch` to return `null` before response construction. Unknown notifications also return `null` and log to stderr for operator visibility. Pinned by `McpProtocolTests.NotificationsInitialized_SpecCompliantForm_ProducesNoResponse`, `NotificationsInitialized_LegacyAlias_ProducesNoResponse`, `UnknownNotification_ProducesNoResponse`, and the spec-level `McpProtocolSourceOfTruthTests.McpDispatcher_KnownNotification_ProducesNoResponse` Theory.

- **INV-MCP-003. Every MCP wire-format constant has exactly one canonical source per side.** Protocol version, JSON-RPC method names, and notification method names live exclusively in `Lifeblood.Connectors.Mcp.McpProtocolSpec`. Clients that cannot take a project reference (Unity bridge today) ship a standalone mirror file compared byte-equal to the spec by ratchet test. Unity mirror: `unity/Editor/LifebloodBridge/McpProtocolConstants.cs`, pinned by `McpProtocolSourceOfTruthTests`. Server consumes the spec directly via project reference: `McpDispatcher.SupportedProtocolVersion` chains to `McpProtocolSpec.SupportedVersion`, `McpDispatcher.KnownNotifications` builds from `McpProtocolSpec.AllKnownNotifications`, the dispatcher's method switch uses `McpProtocolSpec.Methods.*` const cases. Adding a new wire constant: edit `McpProtocolSpec` once; the mirror and consumer ratchets catch every forgotten downstream.

- **INV-MCP-STRICT-JSON-001. Strict JSON mode rejects duplicate object properties before request binding, behind an explicit operator opt-in.** Default mode preserves System.Text.Json compatibility: if a client sends duplicate properties, the normal deserializer behavior applies. `LIFEBLOOD_JSON_COMPAT=strict` is the primary operator switch; the older `LIFEBLOOD_STRICT_JSON` truthy flag remains a backward-compatible strict alias when `LIFEBLOOD_JSON_COMPAT` is unset. In strict mode `Program.cs` routes each stdio frame through `McpJsonRequestParser.DeserializeRequest(..., strictJson: true)` before dispatch. The parser walks the raw UTF-8 JSON with `Utf8JsonReader` and throws `JsonException` on the first duplicate property name in any object, including nested `params` / `arguments` objects. The existing Program parse-error path turns that into JSON-RPC `-32700` with `id: null`, so malformed frames fail at the protocol boundary rather than reaching tool handlers with ambiguous arguments. `LIFEBLOOD_JSON_COMPAT=legacy|warn|strict` is parsed by `ToolJsonCompatibilityModeReader`; unknown values fall back to legacy for deployment safety. Pinned by `McpJsonRequestParserTests` and `ToolArgumentContractTests`.

- **INV-MCP-TRANSPORT-RESILIENCE-001. No single request fault may close the stdio transport for every other call.** `McpServerLoop.RunAsync` keeps one active request per connection, continues reading cancellation notifications for that id, and queues every other frame until the active response is written. A shared daemon runs one loop per persistent client connection; `GraphSessionGate` and `AnalysisRequestCoordinator` own cross-client concurrency. Three fault classes are contained rather than fatal: (1) dispatch faults become id-correlated `-32603` responses carrying `phase` / `method` / `exceptionType` / `recoverable` / `recovery`; (2) a response that fails to serialize still emits a minimal id-correlated error; (3) a broken output pipe is logged and swallowed. Pre-buffered frames are drained after input EOF, while an EOF with no queued work cancels the active request and closes cleanly. Pinned by `McpServerLoopTests` (round-trip, dispatch fault recovery, broken output, malformed JSON, canonical and legacy cancellation, and queued-frame drain).

- **INV-MCP-SHARED-BASE-001. Shared-mode clients with the same explicit pipe consume one daemon-owned MCP host; different pipe names are isolated session boundaries.** `Program` selects ordinary stdio, shared stdio proxy, or shared daemon transport, while `McpServerHost` remains the single composition source for the semantic session and tool graph. A shared proxy forwards JSON-RPC frames without constructing a `GraphSession`; the daemon constructs exactly one `McpServerHost`, so an analyze generation published through one same-pipe proxy is visible through every other same-pipe proxy. A different pipe owns a different daemon and starts at generation zero. Proxy-side malformed JSON returns `-32700` and the proxy continues serving. A daemon forwarding failure is also contained: when restart fails or supervisor-managed mode disables autostart, the proxy returns a correlated recoverable `-32603` frame and remains alive for a later daemon replacement. Killing a generation-1 daemon releases its pipe/mutex and disposes that process-owned session; a replacement on the same pipe begins empty at generation zero. Process integration tests must use unique explicit pipe names and own every daemon process handle so cleanup cannot leave a detached retained graph. Identity/workspace admission, persistent leases/lifecycle, and exact analysis coalescing are strengthened separately by `INV-SHARED-HOST-IDENTITY-001`, `INV-WORKSPACE-BINDING-001`, `INV-MCP-CLIENT-LEASE-001`, `INV-MCP-IDLE-DRAIN-001`, and `INV-ANALYZE-COALESCE-001`. Pinned by `SharedMcpTransportProcessTests` and the reusable `McpProcessTestClient` harness.

- **INV-SHARED-HOST-IDENTITY-001. Pipe-name possession is never sufficient authority to reuse a shared daemon.** Before a persistent connection may forward any MCP frame, proxy and daemon exchange a typed `lifeblood.shared.handshake` carrying shared-protocol version, required capabilities, stable proxy client identity, server informational version, compiled module MVID, and canonical workspace root. The daemon returns its own complete identity and accepts only exact protocol/version/build/workspace equality plus the required capability set; the proxy independently validates the accepted response. The default workspace key walks from the configured key or process directory to the nearest Git worktree root and hashes with operating-system path-case semantics, so agents launched from different subdirectories of one worktree converge without collapsing case-distinct Unix roots. An explicit pipe override remains diagnostic/test routing only and cannot bypass identity. Protocol, build, workspace, or capability mismatch closes that connection and returns a correlated recoverable proxy error without terminating the unidentified daemon. Pinned by `SharedMcpTransportProcessTests.UnsupportedSharedProtocol_IsRejectedBeforeMcpForwarding`, `DifferentSharedBuild_IsRejectedBeforeMcpForwarding`, `SamePipe_DifferentWorkspaceIdentityIsRejectedBeforeMcpForwarding`, and normalized-key same-pipe sharing coverage.

- **INV-MCP-CLIENT-LEASE-001. One accepted persistent proxy connection owns one daemon client lease for its entire attached lifetime.** Shared protocol v2 requires `persistent-connection`, `client-lease`, `request-activity`, `request-cancellation`, `idle-drain`, and `status-v1`; a proxy creates one stable client id, handshakes once per connection, reuses that pipe for every subsequent frame, and reconnects only after the connection breaks. The daemon acquires the lease only after identity/capability admission, rejects duplicate active client identity, wraps every forwarded request in lifecycle activity, and releases the lease when the pipe disconnects. A failed request is never replayed automatically across reconnect because its side effects may already have occurred; the next independent frame may establish a replacement connection. Pinned by `SharedDaemonLifecycleTests.DuplicateActiveClientIdentity_IsRejectedWithoutChangingLeaseCount`, `RequestActivity_UpdatesCountsAndLastActivity`, and `SharedMcpTransportProcessTests.SamePipe_TwoProxiesShareAndPublishLatestGeneration`.

- **INV-MCP-REQUEST-CANCEL-001. Canonical `notifications/cancelled` and compatibility `$/cancelRequest` frames cancel only the matching active JSON-RPC request on that persistent connection.** The stdio proxy continues reading while one daemon response is pending and forwards a matching cancellation notification over the same handshaken pipe; writes are serialized, while exactly one response reader remains active. The daemon maps the target id to a request-scoped token and returns id-correlated `-32800`. `ToolHandler` passes that token as the caller's waiter token to `AnalysisRequestCoordinator`; cancelling one waiter never cancels shared work required by another, while the last departing waiter closes the entry to new waiters and cancels its work token. `GraphSession` checks that token after candidate construction and immediately before publication, so all-waiter cancellation cannot publish a new generation. Pinned by `McpServerLoopTests`, `AnalysisRequestCoordinatorTests.Execute_SynchronousOwnerCancellationStopsAcceptingLateWaiters`, and `SharedMcpTransportProcessTests.PersistentProxy_CancelledAnalyzeDoesNotPublishAndRetrySucceeds`.

- **INV-MCP-IDLE-DRAIN-001. The shared daemon drains only through explicit lease-aware lifecycle transitions.** Releasing the last lease starts an injectable-clock idle deadline; reattachment cancels it, a later last release rearms it, and expiry transitions to draining and cancels the host so accepted client loops finish, the sole `McpServerHost` disposes its retained session, and the process releases its pipe/mutex. A scheduling failure fails safe into drain instead of retaining an ownerless heap. `lifeblood/shared/drain` refuses an ordinary maintenance request while unrelated clients, other active requests, or in-flight analyses exist; only explicit `coordinatedDrain:true` may override blockers. No idle timer starts before the daemon has accepted its first lease, so a zero-idle policy cannot race initial proxy admission. Pinned with fake time by `SharedDaemonLifecycleTests` and at process level by `SharedMcpTransportProcessTests.LastPersistentProxyDisconnect_ZeroIdlePolicyDrainsDaemon` plus `MaintenanceDrain_RefusesUnrelatedLeaseThenStopsExclusiveOwner`.

- **INV-MCP-SHARED-STATUS-001. Capability status reports the active host and lifecycle rather than advertising shared support as active everywhere.** Top-level `lifeblood_capabilities.sharedService` projects the live hosting boundary: active mode, shared protocol version, daemon instance, compiled build identity, process id/start, bound workspace, lifecycle state, client/request/in-flight-analysis counts, last activity, idle policy/deadline, and current working/private memory. Private stdio reports `active:false`, `mode:"stdio"`, no daemon protocol/lifecycle deadline, and its own process facts. Feature flags separately distinguish shared transport support from whether this process is the shared daemon. Pinned by `ToolHandlerTests.Handle_Capabilities_WithoutLoad_ReturnsVersionToolCountsAndContractPaths` and same-pipe process assertions.

- **INV-MCP-SHARED-MATURITY-001. Shared-transport maturity has one machine-readable owner and must match the verified rollout posture.** `ServerIdentity.SharedSessionTransportMaturity` is the server-edge source for `lifeblood_capabilities.featureFlags.sharedSessionTransportMaturity`; its current value is `recommended` because `docs/STATUS.md` names shared mode as the recommended same-workspace configuration, `docs/MCP_SETUP.md` keeps private stdio only as rollback, and `.mcp.json.example` selects `--shared`. Active transport mode remains a separate live fact and does not change maturity. Pinned across the wire by `ToolHandlerTests.Handle_Capabilities_WithoutLoad_ReturnsVersionToolCountsAndContractPaths` and across the public setup surfaces by `DocsTests.SharedTransportMaturity_MatchesCanonicalRolloutDocs`.

- **INV-WORKSPACE-BINDING-001. A shared daemon may publish analysis state only for its canonical bound workspace.** `WorkspacePathIdentity` is the single Server.Mcp seam used by both transport identity and analyze admission. `McpServerHost` binds shared-daemon composition to the handshake root; ordinary private stdio remains unbound. Before `GraphSession.Load`, `WorkspaceBindingPolicy` resolves relative `projectPath` and `graphPath` against that root, requires project analysis to target the root itself, and requires imported graph files to remain inside it. A rejection returns structured `failure:"workspace-binding"` without invoking analysis or changing the committed generation; the last good graph remains queryable. Pinned by `SharedMcpTransportProcessTests.BoundWorkspace_RejectsOutsideGraphWithoutReplacingCommittedGeneration`.

## Tool Registry

- **INV-TOOLREG-001. One typed behavior contract owns every tool's session requirement, externally meaningful effect, and session-lock access; no policy is inferred from tool names. Internal registry records and wire-format DTOs remain separate types.** Every `ToolDefinition` declares `required ToolBehavior Behavior { get; init; }`; omitting the contract is a compile error. The three independent axes are `ToolSessionRequirement` (`None` / `AnalyzedWorkspace` / `WorkspaceRoot` / `RetainedCompilation`), `ToolEffect` (`Observe` / `RefreshWorkspace` / `ManageSnapshotCatalog` / `ExecuteCode` / `PreviewChanges`), and `ToolSessionAccess` (`SharedRead` / `Exclusive`). `SupportsSnapshotRead` is not a fourth authored axis: it is true exactly when the existing contract says `Observe + SharedRead`. `ToolHandler` derives prerequisite rejection, gate selection, snapshot-precondition support, and batch eligibility from that record; `ToolRegistry.GetTools(ToolSessionState)` derives live `[Unavailable...]` description decoration from the same requirement; `lifeblood_capabilities` publishes all 40 behavior contracts and per-axis counts. The old `ToolAvailability ReadSide/WriteSide` split remains only as a derived compatibility projection: `WriteSide` means `RetainedCompilation`, never "mutates state." The wire `McpToolInfo` DTO still has no internal behavior field, avoiding the .NET 8 `[JsonIgnore]`-on-`required init` failure that originally motivated the DTO split. Pinned by `McpProtocolTests.ToolRegistry_EveryToolHasExpectedBehaviorContract`, the empty-session availability ratchet, `ToolHandlerTests.Handle_AllRegisteredTools_UseRegistryDeclaredSessionAccess`, and `ToolRegistry_ToolsList_SerializesWithoutError`.

- **INV-MCP-TOOL-ARG-CONTRACT-001. Tool argument validation lives at the MCP server edge, generated from typed tool input contracts, and never leaks MCP JSON names into Domain or Application.** `ToolInputContractCatalog` is the single source of truth for argument names, JSON types, required flags, array item types, enum values, and per-argument descriptions. `ToolDefinition.InputContract` resolves that catalog entry by tool name and the behavior-derived `SupportsSnapshotRead` fact; the catalog adds the common optional `expectedSnapshotId` / `expectedAnalysisGeneration` fields only to eligible observe/shared-read tools. `ToolDefinition.InputSchema` is generated from the typed contract for `tools/list` / snapshot compatibility; `ToolRegistry` no longer authors anonymous input-schema objects. `ToolArgumentBinder` validates the incoming `JsonElement` before handler dispatch. `ToolRequestBinder` binds high-risk tool inputs (`lifeblood_analyze`, `lifeblood_compile_check`) through typed request records while preserving handler-owned semantic defaults such as `staleRefresh:true`. `legacy` mode accepts current client behavior without diagnostics; `warn` mode accepts but records `lifeblood.tool.arguments` telemetry with unknown / missing / type-mismatch / enum-mismatch / duplicate counts; `strict` mode rejects invalid arguments with an MCP tool error whose JSON body carries `failure:"tool-argument-contract"` and structured diagnostics. This is a server-host contract layer: handlers still own semantic defaults and mutual-exclusion rules, while Domain/Application remain protocol-neutral. Pinned by `ToolArgumentContractTests` (catalog parity, behavior-derived common arguments, generated schema round-trip, no anonymous registry schema authoring, high-risk request-record binding), `ToolSchemaSnapshotTests`, and `ToolHandlerTelemetryTests`.

- **INV-MCP-SESSION-GATE-001. Retained MCP writers are single-flight at the server-host edge; readers lease immutable committed generations instead of blocking writers.** `GraphSessionGate.Write` serializes candidate construction/publication with one host-local writer monitor. `Read` acquires a `WorkspaceSnapshot` lease through the bound `GraphSession`; the request execution context then resolves every graph, analysis, context, generation, profile, and semantic-port property through that pinned host state. A read precondition is compared only after this lease succeeds, against that exact leased `CurrentSnapshot`, and its action is never invoked on mismatch. `ToolHandler.Handle` selects leased read or serialized write directly from `ToolDefinition.Behavior.SessionAccess`; `ToolHandler.GetTools` uses the same leased path. Domain remains concurrency-free, while Application owns snapshot lifetime and the transport-neutral comparison result. Pinned by `GraphSessionGateTests`, registry-declared access tests, live `tools/list` availability tests, and `ToolHandlerTelemetryTests`.

- **INV-SNAPSHOT-PRECONDITION-001. A caller may require an exact committed publication by `expectedSnapshotId`, `expectedAnalysisGeneration`, or both; mismatch is a structured retryable result and never a silently widened read.** `WorkspaceSnapshotPrecondition` and `WorkspaceSnapshotMismatch` live in Application without MCP names. The MCP edge binds and validates the optional fields only for behavior-derived snapshot reads, the gate compares them against the already-leased publication before executing the tool, and the error reports expected/actual id, generation, and canonical analysis identity plus a suggested retry. Existing clients that omit both fields retain latest-snapshot behavior. Pinned by `GraphSessionGateTests.Read_PreconditionMatchesLeasedPublication_AndRejectsAfterRefresh` and `ToolHandlerTests.Handle_ReadPrecondition_AcceptsCurrentSnapshotThenRejectsAfterRefresh`.

- **INV-MCP-READ-BATCH-001. `lifeblood_batch` executes a bounded, fully prevalidated serial query plan under one outer snapshot lease; batch policy derives exclusively from registered tool behavior.** The server rejects an empty plan, more than 32 calls, unknown tools, nested batches, and any tool that is not `Observe + SharedRead` before call zero executes. Accepted calls run through ordinary `ToolHandler` dispatch in stable input order, so prerequisite, argument, envelope, and telemetry contracts are not duplicated. Nested reads reuse the outer request-scoped lease; even when a refresh publishes between subcalls, every nested and outer envelope names the same snapshot/generation/analysis identity. Pinned by `ToolHandlerTests.Handle_Batch_PinsOneSnapshotAcrossForcedRefresh` and `Handle_Batch_RejectsEntirePlanBeforeExecutingAnyCall`.

- **INV-MCP-HISTORICAL-READ-001. Optional `snapshotId` selection leases exactly one current or retained graph-only publication and never falls through to latest when the requested id is absent, evicted, or conflicts with an outer lease.** The MCP binder validates the canonical id and requires it to agree with `expectedSnapshotId` when both are present; `GraphSession` selects under the publication/catalog lock and binds the exact historical committed state to the request execution context. Unknown/evicted ids return structured inventory and latest-id guidance, while nested selection changes reject before batch call zero. Historical graph queries reuse normal handlers and envelopes. Because history contains no source bytes or Roslyn ports, live-source (`partial_view`, invariant-tree reads) and compilation-required tools return their established unavailable-state result instead of combining an old graph with current disk/semantic state. `lifeblood_snapshots` is the exclusive catalog-management edge for list/pin/unpin/evict and optional canonical live-input drift recapture. Pinned by `GraphSessionSnapshotCatalogTests`, `WorkspaceSnapshotCatalogTests`, and the snapshot/history/batch/drift cases in `ToolHandlerTests`.

## Wire Contract

- **INV-WIRE-CONTRACT-001. Every publicly observable wire contract (response envelope, MCP tool input + output shapes, graph JSON schema, canonical id format, parity diagnostic ID set) is pinned by a snapshot ratchet and evolved through the documented deprecation policy.** Pre-policy, Lifeblood's response shapes were tightly coupled to test code that asserted "the response has field X" but had no single ratchet preventing a quiet rename or removal. The first concrete pin lives at `ResponseEnvelopeWireShapeContractTests`: reflects on `Lifeblood.Domain.Results.ResponseEnvelope`, asserts the v1 field set is exactly nine fields with their canonical names and stable type names (TruthTier / Confidence / EvidenceSource / StalenessSeconds / FilesChangedSinceAnalyze / Limitations / AnalysisGeneration / SnapshotId / AnalysisIdentity), and additionally pins every field as `init`-only so mutation after construction is structurally blocked. MCP tool input schemas are pinned by `ToolSchemaSnapshotTests` against versioned files under `schemas/tools/v1/<tool>.schema.json`; the ratchet fails if `ToolRegistry.GetDefinitions()` drifts from the snapshots, if a registered tool has no snapshot, or if the directory keeps a stale snapshot for a removed/renamed tool. The deprecation policy (`docs/SCHEMA_DEPRECATION_POLICY.md`) names the rules: additive changes are allowed without a version bump but require updating the snapshot; renames, removals, type changes, tool removals, enum-member removals are breaking and require shipping v2 alongside v1 with at least one minor release of overlap during which v1 responses carry a `Limitations[]` deprecation notice. NEVER bypass a snapshot drift by editing the expected set without bumping the schema version first; the ratchet exists exactly to prevent that pattern.

## Response Envelope

- **INV-ANALYZE-SKIPPED-PROMINENCE-001. Staleness signals get promoted into envelope `Limitations[]` entries whenever they exceed configured thresholds.** Pre-fix, `ResponseEnvelope.StalenessSeconds` and `FilesChangedSinceAnalyze` were always on the wire but consumers had to compare them against unwritten thresholds to know whether to re-analyze. The seconds + files-changed numbers stayed silent at any magnitude; a 30-day-stale graph emitted the same envelope as a fresh one. The fix routes the always-computed signal through a configurable `StalenessPolicy` (`Application/Ports/Right/IResponseDecorator.cs`) whose two thresholds — `StalenessSecondsWarnThreshold` (default 3600 s = 1 hour), `FilesChangedWarnThreshold` (default 10) — gate explicit `Limitations[]` entries. The composition root (`Server.Mcp.Program`) reads `LIFEBLOOD_STALENESS_SECONDS_THRESHOLD` / `LIFEBLOOD_FILES_CHANGED_THRESHOLD` from the environment at startup so operators tune per-deployment without code change; missing or malformed values fall back to `StalenessPolicy.Default`. The decorator appends staleness limitations AFTER the static per-tool limitations so a consumer reading from index 0 still sees the tool-specific caveats; setting a threshold to `int.MaxValue` / `long.MaxValue` effectively disables the corresponding entry. The unregistered-tool path also honors the policy — missing tool classification does not exempt the workspace from the staleness contract. Pinned by `StalenessPolicyEnvelopeTests` (5 facts: fresh graph emits no extra limitation, staleness-seconds threshold appends entry, files-changed threshold appends entry, custom thresholds override defaults, unregistered tool still surfaces staleness limitation).

- **INV-ADVISORY-LIMITATIONS-001. Every tool — read OR write side — declares an `EnvelopeClassification` in the registry, and every write-side response is wrapped through `WrapWriteSide` so it carries the same `envelope` field as read-side responses.** Pre-S6, `lifeblood_enum_coverage`, `lifeblood_static_tables`, `lifeblood_find_references`, `lifeblood_find_definition`, `lifeblood_find_implementations`, `lifeblood_symbol_at_position`, `lifeblood_documentation`, `lifeblood_diagnose`, `lifeblood_compile_check`, `lifeblood_rename`, `lifeblood_format`, `lifeblood_execute` returned raw JSON with NO envelope on the wire — callers could not distinguish a fresh from a 30-day-stale `find_references` hit list, and tools with documented Unity-runtime blind spots emitted no warning. S6 wires three new classification shorthands surfacing the limitation honestly: `DerivedProvenWithUnityRuntimeRisk` (port_health, authority_report — graph-walk is exact but Unity runtime dispatch invisible to static analysis), `SemanticProvenWithUnityRuntimeRisk` (enum_coverage — serialized-enum fields on prefabs/scenes/SOs can produce values invisibly), `DerivedProvenWithTestDiscoveryRisk` (test_impact — reflection-driven NUnit `[TestCaseSource]`, `[Theory]`, custom test attributes invisible to graph). `WrapWriteSide(toolName, McpToolResult)` in `ToolHandler` is the single seam wrapping every write-side dispatch site through `MergeEnvelopeIntoJson` so envelope shape is uniform across read + write tools. Idempotent: skips error results, skips non-JSON-object payloads, skips already-wrapped responses. The strengthened ratchet `Registry_EveryToolWithEnvelopeWrap_DeclaresEnvelopeClassification` fails when any tool is missing a classification — read or write — so a write-side tool cannot regress into the degraded "Unregistered tool" fallback without the build noticing. LB-TRACK-20260519-026 / S6 atom of the 2026-05-19 plan.

- **INV-DIAGNOSE-FRESHNESS-001. Every read-side response carries the monotonic generation of the exact committed `WorkspaceSnapshot` used by that read.** Pre-S5, two reads taken either side of an auto-refresh were indistinguishable on the wire. A successful full, incremental, or stale refresh creates the next positive generation inside the candidate snapshot; `Clear` preserves the counter, rejected candidates leave it unchanged, and an incremental no-op retains the same snapshot and generation. The value flows through `GraphSession.AnalysisGeneration` into `EnvelopeContext.AnalysisGeneration` and then `ResponseEnvelope.AnalysisGeneration`. Zero before the first load. Generation remains the human-friendly within-daemon counter; `INV-SNAPSHOT-IDENTITY-001` supplies the globally unique cross-workspace/restart identity. Pinned by `ResponseEnvelopeTests`, analyze wire-shape coverage, and the snapshot-reference rollback tests.

- **INV-ENVELOPE-001. Every read-side MCP tool response carries a top-level `envelope` field.** The envelope (`Lifeblood.Domain.Results.ResponseEnvelope`) ships truth-tier (Semantic / Derived / Heuristic / Inferred), confidence band (Proven / Advisory / Speculative), evidence-source string, wall-clock staleness in seconds, files-changed-since-analyze count, a per-tool limitations array, and an `analysisGeneration` monotonic counter (INV-DIAGNOSE-FRESHNESS-001). Population is owned by `IResponseDecorator` (Application port, `LifebloodResponseDecorator` reference adapter); every read-side handler in `ToolHandler` routes through `WithEnvelope(toolName, payload)` (or `MergeEnvelopeIntoJson` for the analyze response) so missing the envelope on a new tool is structurally impossible without bypassing the helper. The decorator's classification table is the single source of truth for per-tool tier/confidence; an unregistered tool falls through to the most-conservative (`Heuristic` + `Speculative`) envelope plus a `Limitations` entry naming the gap, so a missed registration surfaces as an obviously-degraded envelope rather than silent over-confidence. Pinned by `ResponseEnvelopeTests.Decorator_AllReadSideToolsInRegistry_HaveClassification`, which iterates `ToolRegistry.GetDefinitions()` and asserts every read-side tool has a real classification, plus end-to-end tests that read the wire-shape `envelope` field out of `lifeblood_lookup` / `lifeblood_blast_radius` / `lifeblood_resolve_short_name` responses. Closes LB-INBOX-001 + LB-OBS-004.

- **INV-NATIVE-CLANG-ENVELOPE-001. Imported graph envelopes are bounded by adapter capability.** Per-tool envelope classification remains the starting point, but `EnvelopeContext.AdapterCapability` carries the loaded graph's declared adapter capability into `LifebloodResponseDecorator`. Fully proven Roslyn capabilities leave existing envelopes unchanged. External / non-Roslyn graphs append a limitation naming adapter, language, version, and capability fields; if core symbol or call facts are not Proven, a Proven tool classification is downgraded to Advisory. Adapter-less legacy JSON imports are normalized at the MCP session boundary to an explicit `unknown-json-graph` capability so absence of metadata cannot mean "trust like Roslyn." This prevents a native, Python, TypeScript, or other JSON graph from inheriting Roslyn-shaped authority by accident. Pinned by `ResponseEnvelopeTests.Decorator_NativeClangCapability_AddsAdapterLimitsWithoutDowngradingProvenDirectFacts`, `Decorator_BestEffortAdapter_DowngradesProvenToolClassificationToAdvisory`, `ToolHandler_ImportedNativeGraph_EnvelopeCarriesAdapterCapability`, and `ToolHandler_ImportedGraphWithoutAdapterMetadata_GetsUnknownAdapterCapability`.
